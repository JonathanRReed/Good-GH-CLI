# Adversarial review of v1-claude (Plan A) and r1-codex (Plan B)

Reviewed 2026-10-22 against repo `32a3e4b6a1848434e45aa7287bf0ab30d1867ce7` (ggh 0.5.0-beta.2). Code claims verified by reading src/; competitor claims verified by web search and local `gh` probes. Read-only except this file.

## Findings

### 1. [critical] [Plan A] The fix-revert verdict taxonomy silently assumes every PR is a bug fix
**Where**: Plan A, bet 2 ("Evidence verdicts"), verdict list.
**Finding**: The verdict dichotomy (`proven-fix` / `tests-dont-bite` / `fails-on-head` / `inconclusive`) only encodes the SWE-bench "fail-to-pass" relation. Behavior-preserving PRs — refactors, perf, dependency bumps, docs-adjacent code motion — *correctly* pass on base, so every one of them gets stamped "tests do not exercise the change." A fleet that runs "simplify this module" or "migrate to X" tasks will produce a steady stream of false red verdicts in the Desk, training the owner to ignore the signal. The one mechanism the plan hangs everything on becomes noise exactly when the owner relies on it most.
**Evidence**: Plan A bet 2 defines only fail-on-base/pass-on-head semantics. Plan B explicitly handles this ("For a refactor, require selected behavior to remain stable") and cites the fail-to-pass vs keep-passing distinction (https://www.swebench.com/SWE-bench/api/harness/). Agent fleets produce large fractions of refactor-class PRs; A's own wacky #4 (mutation spot-check) would additionally flag pass-to-pass suites as "weak" for the same reason.
**Suggestion**: Infer PR class (or accept `--mode fix|refactor|feature`) and add a `behavior-preserving` verdict: base pass + head pass + no new test failures = green for refactors. Without this, ship the fix-revert verdict only when the PR claims to fix a referenced issue.

### 2. [critical] [Plan A] "Zero configuration for any repo with a test command" has no specified mechanism and omits the hard cases
**Where**: Plan A, bet 2 (fix-revert check) + validation fixture suite.
**Finding**: The check requires four unsolved, unspecified mechanisms: (a) discovering the test command; (b) mapping changed test files → runner arguments per ecosystem; (c) classifying test vs non-test files; (d) constructing "base code + PR tests" reliably. None is spelled out, and the 24-fixture suite (zero tests, skipped, fix-revert true/false, flaky, setup failure) omits precisely the ambiguous cases the rubric names: new symbols failing to compile on base, test-config changes (`vitest.config.ts`, `conftest.py`, `tests/setup.ts`), devDependency additions, shared test helpers, snapshot regeneration, monorepo per-package runners, and non-JS ecosystems.
**Evidence**: File→args mapping differs per runner: `bun test <file>` and `jest <file>` take paths; pytest takes paths; `go test` needs package paths or `-run` filters (no file targeting); `cargo test` needs module/name filters; Maven needs `-Dtest=`. A PR that adds a devDependency its new test imports fails on base's install for a reason unrelated to the fix — indistinguishable from "test exercises the change" without deep parsing, and it can produce a false `proven-fix` (import error on base) or false `inconclusive` (missing dep), depending on where you draw the line. Test-config changes are classified non-test, so a PR whose test depends on a new `setupFiles` mock fails on base for the wrong reason → spurious `proven-fix`. Plan B's experiment F already includes "syntax failure on base," "changed test configuration," and "a passing test that imports no implementation" — A's fixture list has none of these.
**Suggestion**: Retract "any repo with a test command." Ship per-ecosystem adapters (bun/vitest/jest/pytest first — ggh is a Bun repo, so it dogfoods itself), explicit config keys (test command + test-path globs) with heuristic defaults, a rule that non-assertion failures on base (import/compile/config) map to `inconclusive`, and steal Plan B's full fixture taxonomy.

### 3. [critical] [Plan A] Trusted-mode verify executes agent-authored test code with owner privileges, no network isolation, and no threat-model update
**Where**: Plan A, bet 2 trust modes (`--trusted`).
**Finding**: The plan's trust argument — own/agent PRs are "already trusted enough to have been generated locally" — is wrong for this owner. The owner's agents synthesize code from untrusted inputs (issues, web pages, transcripts), so a prompt-injected agent can ship a malicious "test file" inside an otherwise plausible PR. Trusted mode runs it as the user: local worktree, host filesystem, network on, user's GitHub credentials on the machine. Excluding the `.env` copy (fixing `src/services/git/worktree.ts:137-151`) blocks credential *files*, not exfiltration over the network or other host access. The plan also never updates `docs/THREAT-MODEL.md`, whose own rule (line 5) says to revisit the model "when a new command gains network, filesystem, or code execution privileges." `verify` gains all three.
**Evidence**: `src/services/git/worktree.ts:137-151` (env copy the plan disables); `docs/THREAT-MODEL.md:5` (revisit rule) and `:90-100` (non-goals cover same-user processes — meaning ggh deliberately does not defend the host, which makes the trusted-mode description the only place this risk can be addressed, and it isn't). Plan B's experiment E (canary probe, network-off measurement) is the right template even for trusted mode.
**Suggestion**: Trusted mode = worktree + network disabled during the run + explicit "accept residual risk" documentation, plus a THREAT-MODEL section for `verify`. The tests a fleet writes don't need network to bite.

### 4. [critical] [Plan B] The maintainer-cohort adoption program contradicts binding owner decisions
**Where**: Plan B, "Primary user," "Success metric and sequencing," "Distribution and launch."
**Finding**: Recruit five teams, counterbalanced review-time trials, 30% median-time-reduction thresholds, ten enrolled maintainers by day 45, 50 retained teams and 500 challenges/week by month six — this is a funded startup's research program. The binding decisions say: owner is the only user (Q1/Q2), no telemetry ever (Q3), owner uses it daily and validates on their own agent fleet (Q5), agents implement (Q5). Plan B optimizes a product the owner was explicitly told they aren't building.
**Evidence**: `/tmp/ggh-plan/decisions.md` Q1-Q5; Plan A's rebuttal point 2 is correct on this. Plan B's own admission that the repo's "only observed user cannot establish this adoption thesis" (r1 §1.2) cuts against its own sequencing.
**Suggestion**: Keep Plan B's *internal* demand tests (experiment D "does ggh beat a small gh script," experiment F fixture taxonomy) but run them on the owner's fleet and public release, not a recruited cohort.

### 5. [warning] [Plan A] Sequencing deletes `notifications` and `triage` at step 1 but their replacement (Desk) arrives at step 4
**Where**: Plan A, subtractions ("notifications (folded into Desk)") vs sequencing (subtract = step 1, Desk = step 4).
**Finding**: The owner is a daily driver (Q5). Between step 1 and step 4 — which spans verify, the agent loop, and MCP/skill shipping — they have no notification flow at all. This is a self-inflicted regression in the product's core "use it daily" claim, and it violates the plan's own subtraction rationale (cutting is about focus, not amputation ahead of the replacement).
**Evidence**: `src/commands/notifications.ts:9-12` (command exists today); Plan A sequencing lists Desk at position 4; v1 subtractions list notifications under "folded into Desk."
**Suggestion**: Fold-and-delete in the same step, or keep `notifications` until the Desk ships.

### 6. [warning] [Plan A] The fix-revert verdict is adversarially gameable and A doesn't downgrade it for untrusted PRs
**Where**: Plan A, bet 2 verdicts + trust modes.
**Finding**: The mechanism only measures fail-on-base/pass-on-head of tests the *author* chose. A motivated author can ship a test that imports a PR-added symbol but asserts nothing about the fix, or that fails on base for an unrelated reason, and reliably earns `proven-fix`. Fine when the threat is agent sloppiness (the owner's fleet); wrong when the verdict is shown to strangers reviewing foreign PRs. A prints the trust mode but keeps identical verdict semantics across modes, so `proven-fix` on a `--isolated` foreign PR still reads as proof.
**Evidence**: Plan A bet 2 defines the verdicts without provenance-of-test semantics; Plan B is built around exactly this objection (reviewer supplies test bytes; "It cannot certify its own claim").
**Suggestion**: Per-mode verdict labels (`proven-fix [trusted]` vs `differential-pass [author-tests]`), and never display `proven-fix` from author-authored tests on foreign PRs — keep Plan B's reviewer-controlled `challenge` as the escalation path there.

### 7. [warning] [Plan A] Base semantics are unspecified: merge-base vs target tip changes both cost and meaning
**Where**: Plan A, bet 2 ("bound to exact base/head/test OIDs; invalidated when any change").
**Finding**: If "base" means the target branch tip, every push to main invalidates every open PR's verdict — re-run storms for a fleet, and constant churn in the Desk's ranking. If it means the merge-base, the verdict says nothing about whether the PR still integrates. The plan doesn't say which, and "invalidated when any change" suggests the author hasn't noticed the distinction.
**Evidence**: Plan B resolves this explicitly: recorded merge-base vs PR head "to isolate the contribution," with integration tested as "a separate run against a recorded synthetic merge result" and "a conflict makes that run inconclusive."
**Suggestion**: Adopt Plan B's split verbatim; it is the single best technical paragraph in r1.

### 8. [warning] [Plan A] Bet 3's "agent-side wedge" overstates novelty: the official GitHub MCP server already resolves review threads
**Where**: Plan A, bet 3 (`ggh pr feedback` / `pr address` + MCP tool set).
**Finding**: "Any agent can close the review loop without scraping" is already true via the official github-mcp-server: it queries review threads and ships `resolve_thread` / `unresolve_thread` (merged 2026-03-13) plus Copilot-thread resolution reasons (2026-08-27). Building a parallel MCP tool set for thread reading/reply/resolving duplicates a maintained, official surface — and loses, because vendor agents will support the official one first.
**Evidence**: https://github.com/github/github-mcp-server/pull/1919 ; https://github.com/github/github-mcp-server/pull/3123 ; ggh's own MCP surface today is a read-only set (`src/commands/mcp.ts:7-181`: status, pr view/list, issue, checks, stack, notifications, commits, diff).
**Suggestion**: Reposition bet 3's delta honestly: the *contract* (verdict envelope feeding `--agent`, and the thread → fixing-commit → verdict binding in `pr address`), not thread plumbing. Where possible extend or wrap, don't reimplement.

### 9. [warning] [Plan A] Bet 3 contradicts ggh's documented read-only MCP design
**Where**: Plan A, bet 3 ("Ship as an MCP tool set") vs `src/services/mcp.ts:40`.
**Finding**: The MCP transport is annotated "deliberately read-only MCP surface," and `ggh mcp` rejects `--agent`. `pr address` is a write (reply + resolve). Making it an MCP tool flips a deliberate security decision with zero acknowledgment of what a connected agent may now write on the user's behalf.
**Evidence**: `src/services/mcp.ts:40`; `docs/THREAT-MODEL.md` trust-boundary table (ggh→GitHub confirmation rules); README.md:252 (MCP rejects `--agent`).
**Suggestion**: Either keep MCP read-only and expose `pr address` via CLI/skill only, or write the threat-model paragraph first (which writes are MCP-eligible, what identity/confirmation applies).

### 10. [warning] [Plan A] Desk before ship inverts the complexity budget, and the repo's own prototype evidence is against the Desk
**Where**: Plan A, bets 1/4 and sequencing (Desk = 4, `ship` = 5).
**Finding**: `ship` is a composition of existing, behavior-tested parts: branch-offer on main (`src/commands/commit.ts:570`), commit→PR via the publication service (`src/services/publication.ts`), `checks --watch` (`src/commands/checks.ts:16`), `pr merge --auto` (README.md:78), worktree checkout, operation recovery. It is the cheapest bet on the board and the most direct daily-use item for Q5. The Desk, by contrast, is a new cross-repo TUI whose closest sibling in this repo — the keyboard stack view — was prototyped and excluded on 2026-10-15 for "no demonstrated advantage over stack list and inspection commands." Its incumbent competitor (gh-dash, 12k stars, actively shipped merge-queue indicators and workflow approvals in v4.23.0) already covers queue + actions + merge. Ordering Desk before ship spends the scarce complexity budget on the riskier, less differentiated bet first.
**Evidence**: `docs/quality/2026-10-15-prototype-decisions.md:12` (keyboard stack view excluded); https://github.com/dlvhdr/gh-dash and https://github.com/dlvhdr/gh-dash/releases/tag/v4.23.0 ; existing parts verified in src/commands and README.md:78.
**Suggestion**: Move `ship` to step 2-3. Desk moves after dogfooding produces evidence that the owner's PR queue actually hurts — per the repo's own rule ("retain an experiment only when it improves an observed task").

### 11. [warning] [Plan B] `challenge`'s reviewer-authored regression test is the highest-friction default imaginable
**Where**: Plan B, "Primary user and this week's install reason," bet 1.
**Finding**: The first-run experience requires the maintainer to *write a regression test for someone else's PR* (`--test-file ./review/bug-184.test.ts`). Writing a correct failing test is often more work than reviewing the diff — it inverts the owner's real loop, where agents write tests and the human audits them. As the default verification primitive, it is dead on arrival for daily use; Plan B's own experiment D ("does ggh beat a small gh script") applied honestly would likely kill it.
**Evidence**: Plan B bet 1 and the install-reason paragraph; contrast Plan A bet 2, which needs zero reviewer labor to answer the same trust question for own-agent PRs.
**Suggestion**: A's fix-revert is the default; B's reviewer-controlled challenge is the escalation for disputed or adversarial PRs. Both belong in one product; neither works as the only mode.

### 12. [warning] [Plan B] A Docker-required runner for *all* verification conflicts with the lean-local constraint and the owner's daily loop
**Where**: Plan B, "Execution boundary."
**Finding**: "Initially support a pinned Linux runtime with documented Docker-compatible prerequisites," with a plain-worktree fallback rejected because it "would silently erase the product's trust claim." For a stranger's PR, B is right. For the owner's own agents' PRs — the dominant case per Q5 — it makes every `verify` pay a container spin-up on macOS (Docker Desktop/colima dependency, Linux image pulls) for code that was generated on this machine anyway. It converts the daily loop into a heavyweight ceremony, violating the spirit of Q3 ("lean single local process").
**Evidence**: `/tmp/ggh-plan/decisions.md` Q3, Q5; Plan B execution boundary section; Plan A's rebuttal point 4 already lands this correctly (two trust modes, labeled honestly).
**Suggestion**: Two trust modes (A), with B's isolation discipline — canary probe experiment E, no mounts, network off — applied when the isolated mode is eventually built (A's step 8).

### 13. [warning] [Both] Both plans overstate the novelty of their reproducer/test-first bets and ignore shipped precedent
**Where**: Plan A wacky #2 (test-first issues) and wacky #4 (mutation spot-check); Plan B wacky #1-2 and bet 3.
**Finding**: Neither plan positions against tools that already ship adjacent capability: `ordeal` (PyPI) does scan → reproducible failing witness → saved pytest regression → `verify` — literally "find a real failure, keep it fixed," which is Plan B wacky #1 and most of Plan A wacky #2. `pramaan` is an early-stage "receipt-first verification layer for code review" with sandbox evidence, differential replay, mutation, and a GitHub Action wrapper. `difftest` does differential testing for AI rewrites. The ai-sdlc project merged sandboxed differential test execution (base + PR-diff + both test suites, fail-closed parsing) in June 2026. The techniques are in active circulation; the plans' claims should be scoped to what's actually new (zero-config, PR-flow-integrated, multi-ecosystem), and B's own honesty rule — "if a script does it just as well, ship the script" — applies to its own bet 1 as much as to anything else.
**Evidence**: https://github.com/teilomillet/ordeal ; https://github.com/tsinghkothari-droid/pramaan ; https://github.com/nalediym/difftest ; https://github.com/ai-sdlc-framework/ai-sdlc/commit/68b84a24ba8a33a0a6b2ad5a87db66be4ad0a553 .
**Suggestion**: Name the prior art in the plan and public positioning; differentiate on the owner-loop integration, not on "nobody does this."

### 14. [warning] [Plan A] No distribution channels for a plan whose stated goal is adoption
**Where**: Plan A, validation + sequencing step 7 (launch).
**Finding**: Q1 defines success as installs, stars, and contributors — yet v1 silently dropped v0's entire distribution section (Homebrew tap, npm, `gh extension install`, MCP registry, skill packs) and replaced it with "Public: launch with 3 real agent PRs." That's a measurement, not a channel. A stranger who sees the launch artifact has no specified path from interest to installed binary. Plan B, whatever its other problems, keeps npm-first, a `gh` extension, and a skill.
**Evidence**: v0-claude.md "Distribution" vs v1-claude.md (absent); `/tmp/ggh-plan/decisions.md` Q1; README.md:26 ("Use `bun add -g good-gh-cli@<version>` only when that release's notes confirm npm publication" — npm publication is currently disabled, so the cheapest channel has a known blocker neither plan schedules).
**Suggestion**: Put one channel (npm publication + release-notes fix, or a Homebrew tap) into the launch step with an owner; everything else can wait.

### 15. [nit] [Plan A] Wacky ranking ignores feasibility: `race` (#1) needs a provider mode that doesn't exist; `issue repro` (#2) is buildable today
**Where**: Plan A, wacky ideas list.
**Finding**: The list is ranked "by expected value," but `race` requires driving installed agent CLIs *agenticly* (tools on, long sessions, per-provider protocols) — today's adapters are deliberately non-agentic: Claude runs `--print --safe-mode --tools "" --disallowedTools "*" --no-session-persistence` (`src/services/ai/claude.ts:39-40`), Codex runs one-shot `exec --ephemeral` (`src/services/ai/codex.ts:44-59`). Plan A itself concedes it's "a later bet." Meanwhile `issue repro` needs only a tool-disabled text proposer, which Plan B bet 3 confirms is implementable now.
**Evidence**: cited file:line; Plan A bet 2 "Later: ... AI-proposed reproducer tests."
**Suggestion**: Rank by expected value *at achievable feasibility*: repro first, race parked until an agentic provider mode exists.

### 16. [nit] [Plan A] "Mutation spot-check ... novel UX" overclaims
**Where**: Plan A, wacky #4.
**Finding**: Mutation results in the PR review flow are already shipped: Infection posts GitHub annotations for escaped mutants in changed files; Tautest does changed-line-scoped Stryker with sticky PR comments and AI fix prompts; Stryker incremental PR runs and `--break-at` gates are standard.
**Evidence**: https://deepwiki.com/infection/infection/8.4-cicd-integration ; https://github.com/canblmz1/tautest/releases/tag/v1.0.0 .

### 17. [nit] [Plan A] Native stack "interop" is framed as a swap but is actually a state migration
**Where**: Plan A, bet 5.
**Finding**: ggh's stack model stores parents in git config (`branch.<name>.gh-merge-base`, `src/services/git/stack.ts:265-279`; worktree adds record parents at `src/services/git/worktree.ts:166-173`) and has its own conflict recovery (`restack --continue/--abort`). `gh stack` keeps separate local tracking and GitHub-native stack linkage, requires gh ≥ 2.90, and its documented command set (`sync`, `rebase`, `modify`, `merge`) has no documented conflict `--continue` analog. "Replace" means migrating branch-relationship state between two tools with different sources of truth, plus deciding which tool owns recovery mid-conflict — the plan's probe-first framing is right but under-scoped.
**Evidence**: https://docs.github.com/en/pull-requests/reference/stacked-prs-cli-commands ; https://docs.github.com/en/pull-queries/reference/stacked-prs ; stack.ts and worktree.ts citations above.
**Suggestion**: Write the interop as: gh stack owns remote/stack linkage; ggh keeps only local conveniences it can prove gh stack lacks after the probe; define the migration and the exit path.

### 18. [nit] [Plan B] "Reuse `publication-approval`" for acceptance binding is an extension, not a reuse
**Where**: Plan B, bet 5.
**Finding**: `publicationSnapshot` hashes the plan plus content bytes (`src/services/publication-approval.ts:20-40`); it has no slot for an acceptance result, and `--yes`/`--approve-plan` remain caller-authorized (`src/commands/pr-create.ts:118`). Binding verdicts into the snapshot is a new field plus a new invalidation rule ("changing the patch after testing invalidates the binding"), not reuse.
**Evidence**: cited file:line.
**Suggestion**: Say so concretely: schema addition + invalidation rule, or the bet under-costs itself.

## Missed opportunities

1. **Ship the fix-revert check as a GitHub Action (high, not wacky).** The check is deterministic and CI-shaped: on every PR, check out base, overlay PR tests, run, comment. This is the one ggh feature that is *more* valuable in CI than locally — GitHub's own runners are the `--isolated` sandbox Plan A defers to step 8, for free, solving the foreign-PR trust problem that both plans spend the most ink on. It is also the only channel where strangers get value with zero install friction, which is Q1's whole point, and it makes verdicts exist automatically so the Desk can rank by them. Neither plan mentions CI distribution of the core differentiator; Plan A's step 8 builds the hardest possible version (local container isolation) of what an Action gets for nothing on public repos.
2. **Commit-status verdicts via the existing `gh` token (med-high, not wacky).** Plan B rightly notes check-runs need App-level permissions, and Plan A offers only an optional PR comment — a comment nobody sees at merge time. The Commit Statuses API works with ordinary repo-write credentials and renders in the merge box, where it can be made a required check. Cheap, visible, no App, no server; neither plan names it.
3. **Agent standings ledger (high, wacky).** The owner's actual meta-question is "which agent/model should I give this task to, and which PRs can I skim?" ggh already records provider/model usage per operation (README.md:322) and would now see verify verdicts and review-thread rework per PR. A local, private, no-telemetry standings view — agent/model → verified-fix rate, tests-dont-bite rate, review rework, diff size — is a one-table feature on data the tool uniquely sits on top of. Neither plan notices that the fleet's quality history is an asset ggh can own and nothing else can. It also feeds `race` later.
4. **Local fleet dashboard (med-high, mildly wacky).** The Desk covers the remote half (PRs awaiting review) but the owner's day starts local: N worktrees, N running agent sessions, dirty trees, stale branches, which sessions finished and are ready to `ship`. A `ggh fleet` view over worktree list (`src/services/git/worktree.ts:51-82`) + branch state + operation records is cheap, daily-use surface that neither plan has, and it's where `race` would live when it exists.
5. **Flake ledger (med, not wacky).** Both plans treat flakiness as a fixture case; neither persists it. Across repeated verify runs, ggh can learn which tests are flaky on the owner's repos, then improve verdicts ("fails-on-head; test known-flaky 2/5 runs"), Desk ranking, and blame assignment (don't punish the agent for a flaky suite). Small, deterministic, compounds silently.
6. **Public "verify gauntlet" corpus (med, wacky).** An adversarial corpus of PRs with ground-truth verdicts — tests that lie, tests that import nothing, spurious base failures, refactors, flaky — published as both the fixture suite and the launch artifact, with any competitor (mutation tools, ordeal-style reproducers, LLM reviewers) runnable under equal conditions. This is v0's "incident corpus" idea reborn in an honest, on-thesis form: the marketing artifact *is* the test suite, and it can embarrass ggh too, which is the only kind of comparison Plan B would accept as evidence.
7. **Promote `issue repro` out of the wacky list (high).** Covered in finding 15, but as opportunity: the acceptance-test-before-fix loop is the single biggest workflow upgrade for an agent fleet — every fix becomes verifiable by construction, and `race`, `verify`, and review all inherit it — and it is buildable *now* with the existing tool-disabled adapters. It should be the first AI-era bet, not wacky #2.

## A vs B verdict

**Primary customer.** A is right: Q2 makes humans-at-terminal and agents the first-class users and maintainers "a little," and the owner's own loop (agents produce, owner reviews) is the same bottleneck B targets. B's insight — reviewer verification is the wedge — was correct and A absorbed it; B's *segment* (external maintainers of 10-PRs/week Node projects) is the secondary audience promoted to the entire product. B loses on the binding decisions, not on the analysis.

**Validation method.** A is right given Q3 (no telemetry) and Q5 (owner uses it daily): dogfooding across the owner's fleet plus a public release is the only validation program consistent with the constraints. But A's external-feedback loop is thinner than B's — B's experiments D (beats a script) and C (vs current practice) are genuinely good designs and should be run scaled-down on the owner's own PRs as internal kill gates.

**Execution trust model.** A's two trust modes are the right structure for this owner; B is right that a worktree is not an isolation boundary and must never be labeled one. B's "a plain worktree fallback would silently erase the trust claim" is true for foreign PRs and irrelevant for the owner's own agents' output. A's deferral of `--isolated` to step 8 is coherent pre-1.0, but finding 3 stands: trusted mode still needs network-off and a threat-model update.

**Who writes the test.** A's fix-revert (author's tests, zero reviewer labor) is the correct default for the owner's fleet, where the threat is sloppiness. B's reviewer-controlled test is the correct mechanism for disputed or foreign PRs, where the threat is deception — and it is too much friction to be anyone's default (finding 11). Verdict: A's default, B's escalation, with A adopting per-trust-mode verdict labels so author-tests never read as proof on foreign PRs.

**Compatibility and deprecation.** A is right: Q4 says cut hard and break freely pre-1.0, with zero external users to hurt. B's "preserve compatibility until a justified deprecation" optimizes for a user base ggh does not have and contradicts a binding decision.

**Base semantics.** B is right and A should adopt it verbatim: recorded merge-base vs head to isolate the contribution, plus a separate synthetic-merge integration run, with conflicts marked inconclusive. A's "invalidated when any change" is under-thought and would either storm or mislead (finding 7).

**Subtraction and command count.** A is right in substance — the rationale is duplicate `gh` proxies creating reader load in README, completion, docs, and tests, which matches the repo's own path-to-ten guidance ("complete and polish those journeys before expanding the command catalog"); B's rebuttal (#25) attacks a numeric strawman. B is right that behavior-bearing commands (e.g., `secret`'s hidden-input handling) deserve a capability check before deletion, which A's probe already concedes. A's genuine sequencing bug is the notifications gap (finding 5).

**Novelty claims.** B is the more honest document about prior art (SWE-bench, mutation testing, CI runners) and correctly demolished v0's stacks differentiator — A verified and conceded it. A is more honest about the owner. Both missed current shipped/adjacent tools (finding 13), and A's biggest overclaim is bet 3's MCP wedge, since the official GitHub MCP server already resolves threads (finding 8).

**Metrics.** B's 30% review-time reduction and retained-team counts are unfalsifiable under a no-telemetry constraint and scaled for a company that doesn't exist; A's downloads/stars/issues-from-strangers are consistent with Q1 but under-specified, and neither plan names a distribution channel (finding 14). Net: A's framework wins, B's experiment designs win — take the experiments, run them on the owner, and add one channel to the launch step.
