Tricks worth stealing for a CLI, ranked by value to ggh:

1. Separate base, upstream and publish identity. Preserve `gh-merge-base`, record the selected comparison remote, and push explicit destinations. ggh already reads push-remote settings and stack parent metadata. Audit the mismatch case `feature` tracking `origin/main`, plus fork remotes, rather than adding a second branch model.
2. Build a review-conversation command around GraphQL node IDs. Offer list/reply/resolve/unresolve, structured JSON including outdated/resolved state, and explicit mutation targets. Keep posting a fix and resolving its discussion separate. This is useful inside every agent host.
3. Preview without touching the index. Extend T3's temporary-index technique to commit planning and AI input. ggh already uses a temporary index in `src/services/git/split.ts`; reuse it. Preserve intentional partial staging when committing.
4. Steal clone diagnostics and lifecycle details. Parse progress, retain the meaningful stderr tail, classify SSH failures, disable hidden prompts, support explicit protocol choice, and guard cancellation cleanup. ggh already has repository search and standard/shallow/blobless selection in `src/commands/clone.ts`; keep those advantages. Do not require a background service merely to imitate a toast.
5. Cooperate with T3 watches. After ggh creates a PR, return canonical URL, host/repository and head SHA. Let the calling agent invoke `link_pull_request` for each layer and `watch_pull_request` when asked. A shell CLI must not claim it registered a PR without a T3 receipt.
6. Centralize request budgets and identity. Port credential-scoped cache keys, typed retry times, conditional reads and bounded batching through `gh api` first. Do not replace the `gh` dependency just to copy T3's HTTP implementation.
7. Report remote outcomes precisely. T3 rereads state after merge because success may mean queued/auto-merge enabled. ggh should return `merged`, `queued`, `auto_merge_enabled`, or `unknown`, with identifiers, instead of treating subprocess exit zero as completed merge.

What T3 Code does not fully provide, ranked opportunities:

1. Uniform approval tied to the reviewed head. Make ggh merge plans include host/repository/PR/head SHA and enforce `gh pr merge --match-head-commit`. Reject a moved head and require renewed review. T3 ordinarily merges the fresh head, which can differ from the reviewed head. ggh currently also lacks this flag in `src/services/github/prs.ts:190`; this is unfinished work, not an existing advantage.
2. Durable, portable stack-operation recovery. T3's cascade reports completed layers and aborts the conflicting temporary rebase, but earlier pushes remain remote. The inspected implementation has no durable resume journal for that operation. ggh already has `StackRecoveryCheckpoint`, locks and protected refs in `src/services/git/stack.ts`; extend and qualify that advantage rather than starting over. Cover process death after a push and remote movement before resume.
3. A terminal-native review protocol. T3 already resolves threads and submits reviews. The gap is reusable CLI JSON, exit codes, batch selection, dry-run plans and exact review targets across T3/Codex/Claude. Avoid advertising "review resolution" itself as a T3 omission.
4. Preserve the human index contract. T3's file selection stages complete files and can reset other staged selections. ggh can explicitly support staged-only, selected files and selected hunks, with previews that bind to content. This matters when a human and agent share a checkout.
5. Rich acquisition controls. ggh already exceeds this inspected Add Project flow in repository search and shallow/blobless modes. Add protocol-aware diagnostics and optional sparse paths if justified. T3 already handles destination validation, progress, cancellation and retries; those are not open territory.
6. Cross-process coordination and recovery. T3's leases cannot constrain an unrelated terminal or an agent's raw Git. ggh can expose repository-common-directory operation locks, expected refs and resumable outcomes for its own mutations. It cannot promise to serialize arbitrary external Git either.
7. Durable "changes since review" baselines. T3 already has per-commit diffs and stale viewed-file marks. A CLI can store reviewed base/head SHAs, compare later pushes, detect rebases and make outdated discussion anchors explicit. This is more useful than reproducing T3's graphical diff renderer.

Specific answer: merge best practice

T3 refreshes GitHub action state before merging. Branch update always sends `expectedHeadOid`. Ordinary merge only adds that field when optional agent-credit removal actually changes the merge body. With credit removal off, rebase selected, or no text changed, the field is absent. Fresh reading narrows the race but does not bind the mutation to the user's previously reviewed SHA. [G/GitHubPullRequestApi.ts:2554–2618][merge]

A merge queue forces the auto-merge mutation. Explicit auto-merge also uses it while the PR is not immediately mergeable; otherwise it merges directly. Native stack merge first validates expected heads for affected open layers, then sends the target SHA to `pulls/<number>/merge-async` and polls its operation for up to five minutes. Cascading restack uses `--force-with-lease=refs/heads/<branch>:<reviewed-sha>`. Copy the explicit leases and state confirmation; strengthen ordinary merge pinning. [stack][stack], [restack][restack]

Specific answer: review thread resolution

T3 calls `resolveReviewThread` or `unresolveReviewThread` with the GitHub thread node ID. The service checks host support and viewer permission. The UI additionally checks the thread's `canResolve` field. Thread reads carry IDs, resolved/outdated state, path/side/line and paginated comments. Replies use a separate mutation. No automatic "fix committed, therefore resolve all threads" behavior was found in the traced workflow. A ggh implementation can use the same GraphQL mutations through `gh api graphql`; a new authentication system is unnecessary. [service][resolution], [mutations][resolveapi]
