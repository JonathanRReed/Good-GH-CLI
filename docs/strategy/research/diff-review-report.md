# ggh Review Surfaces — Survey & Recommendations (Oct 2026)

Research for Good GH (`ggh`): a Bun/TS CLI (commander + picocolors + @clack/prompts only) compiled with `bun build --compile`, already fetching PR diffs (`ggh pr diff`, `renderDiff` in <ref_file file="/Users/jonathanreed/Downloads/Good-GH-CLI/src/utils/output.ts" />) and posting reviews via GraphQL. The question: is a diff-reading surface for humans worth building, and if so which 2–3, given the owner's bar ("truly first-class or don't bother")?

## Landscape snapshot (what's real in Oct 2026)

**Renderers/pagers.** [delta](https://github.com/dandavison/delta) 0.20.1 (Oct 4 2026, MIT, 32k★) is the standard: bat-grade syntax themes, Levenshtein word-level intraline, side-by-side with wrap, `n`/`N` file/hunk navigation, hyperlinks that can deep-link `file:line` into editors, and — new in 0.20.x — [OSC 1717](https://github.com/jesseduffield/lazygit/pull/5731) diff-line metadata so a host TUI can embed delta's rendering while keeping its own keybindings/selection. [difftastic](https://github.com/wilfred/difftastic) 0.71 (Sept 2026, MIT, 26k★, active) is the structural (tree-sitter AST) diff: it handles reformats, moved code, and renames far better; the README's own "Known Issues" admit it "scales relatively poorly on files with a large number of changes" — relevant at 5k+ churned lines. [diff-so-fancy](https://www.npmjs.com/package/diff-so-fancy) revived in 2026 (1.4.14, Oct 18) and now also emits OSC 1717, but it's line-styling only — no highlighting, no split view. [riff](https://github.com/walles/riff) is a capable but small pager; [diffsitter](https://github.com/afnanenayet/diffsitter) self-describes as "nowhere close to production ready".

**TUIs.** [tuicr](https://github.com/agavra/tuicr) (MIT, Rust, created Jan 2026, 3.4k★, 0.27 in Sept) is the full product: GitHub-style continuous diff, vim keys, line/range/file/review-level comments, persisted review tracking, and `:submit` pushes a **real GitHub review** via `gh`. [diffnav](https://github.com/dlvhdr/diffnav) (MIT, Go/BubbleTea) is delta's rendering plus a GitHub-style file tree, `o` opens `$EDITOR` — read-only. Smaller Rust entrants: [lumen](https://github.com/jnsahaj/lumen/) (tree-sitter, "snappy on multi-thousand-line diffs", GitHub PR support, annotations), [gh-review](https://github.com/Neville-Loh/gh-review/), [clabby/critic](https://github.com/clabby/critic).

**The Bun/TS stack that matters.** [OpenTUI](https://github.com/anomalyco/opentui/) (MIT, 13.5k★, created Jul 2025; Zig core + TS/React/Solid bindings, flexbox, mouse, prebuilt binaries for 8 platforms; "OpenCode uses it in production") has become the foundation for a cluster of Bun-native diff viewers: [critique](https://github.com/remorse/critique) (MIT, 1.3k★, TUI **and** web previews, fetches GitHub PRs), [hunk](https://github.com/modem-dev/hunk/) (MIT; explicitly "built on OpenTUI and Pierre diffs", file sidebar, split/unified/auto, watch mode, git-difftool support), and [stage](https://github.com/nikok6/stage). "Pierre diffs" is [`@pierre/diffs`](https://www.npmjs.com/package/@pierre/diffs) (Apache-2.0, v1.6.1 published days ago, maintained by Bootstrap/Twitter alumni): Shiki-based highlighting (JS-regex engine default), split/stacked, char/word intraline, **annotation framework for injecting comments**, virtualization, ~2.4MB unpacked ([registry](https://registry.npmjs.org/@pierre/diffs)). **T3 Code itself renders diffs with `@pierre/diffs` + `@pierre/trees`** ([apps/web/package.json](https://raw.githubusercontent.com/pingdotgg/t3code/main/apps/web/package.json)) — the same library a ggh web/TUI surface would use is what the strongest agent host already ships. By contrast, [Ink](https://github.com/vadimdemedes/ink) is a known perf trap for dense redraws (object-per-cell, string-level diffing; Claude Code forked it beyond recognition; the incremental-rendering [PR #751](https://github.com/vadimdemedes/ink/pull/751) was closed unmerged — see [analysis](https://visulima.com/docs/packages/tui/why-is-ink-slow)). Don't build a 5k-line diff surface on Ink.

**Editors.** `code --diff a b` works ([docs](https://code.visualstudio.com/docs/editor/command-line)); one diff per invocation ([vscode#175479](https://github.com/microsoft/vscode/issues/175479)). `cursor --diff` mirrors it. `zed --diff old new` is **repeatable** — one invocation, many diffs ([CLI reference](https://zed.dev/docs/reference/cli)). JetBrains ships `idea diff a b` ([docs](https://www.jetbrains.com/help/idea/command-line-differences-viewer.html)). `git difftool` accepts any external via `--extcmd`/`difftool.<t>.cmd` ([git-difftool](https://git-scm.com/docs/git-difftool)); difftastic documents its [difftool config](https://difftastic.wilfred.me.uk/git.html); lazygit documents delta/difftastic as pagers with `lazygit-edit://` hyperlinks ([Custom_Pagers](https://github.com/jesseduffield/lazygit/blob/HEAD/docs/Custom_Pagers.md)). The killer editor asset is the [GitHub Pull Requests extension](https://marketplace.visualstudio.com/items?itemName=GitHub.vscode-pull-request-github) (Microsoft-maintained): multi-diff review UI, in-editor commenting, file-viewed sync to GitHub, easy PR checkout.

**Web viewers.** [@pierre/diffs](https://diffs.com) (best-in-class; used by T3 Code); [git-diff-view](https://github.com/MrWangJustToDo/git-diff-view) (MIT, 86k weekly dl, React/Vue/Solid/Svelte, web-worker highlighting; one project swapped 35 Monaco instances "5MB+ each" for it at "~40kb" — [commit](https://github.com/dcouple/Pane/commit/3fe09a184ba8618452354ebe731b1583ecb246f9) — while [another went the opposite way](https://github.com/johannesjo/parallel-code/commit/ad987c700856c6f0021ab6e65fb5b33ac7cce657) wanting search/virtual scroll); [diff2html](https://www.npmjs.com/package/diff2html) (MIT, 287k weekly dl, mature but documented OOM/slowness on large diffs); Monaco (VS Code-grade but heavy). [Shiki](https://shiki.style/guide/bundles) full bundle is 6.9MB/1.3MB gzip — use fine-grained imports.

**GitHub web free baseline.** Files-changed gives "Show changes since your last review", Viewed checkboxes with progress bar (persisted across machines), commit-range selection, split/unified, whitespace hiding, file tree, line-range comments and suggestions ([GitHub docs](https://docs.github.com/en/pull-requests/how-tos/review-pull-requests/reviewing-proposed-changes-in-a-pull-request); [SO](https://stackoverflow.com/questions/48060812/reviewing-only-changes-i-did-not-review-before)). Strong tracking; mediocre rendering; requires round-trip + your code on someone's tab.

## Recommendations — 2–3 surfaces, `ggh review 42 --tui|--editor|--web`

The unifying idea: **ggh owns review state and posting; it never owns diff rendering.** Rendering is a solved problem (delta/difftastic terminal-side, @pierre/diffs screen-side); the unsolved part for a CLI is the review loop — capture, anchor, persist, submit — which ggh's GitHub service layer already has.

### 1. `ggh review 42 --editor` — build first (days, not weeks)
The floor is genuinely high: editors do char-level intraline, scroll-blazing virtualization, and go-to-definition — the thing *no* diff viewer, including GitHub web and T3 Code, can match, because it's not a diff viewer at all.

Architecture: `ggh review 42 --editor` → resolve PR → checkout into a worktree (reuse `ggh worktree`/`pr checkout`) → detect editor (`$GHH_EDITOR` > `$EDITOR` > `zed`/`code`/`cursor`/`idea`) → open worktree dir. With VS Code + the GitHub PR extension, the user gets the complete loop — multi-diff, inline comments that post, viewed-file sync — for free; ggh's job is just to get the right worktree open. For non-VS Code editors, register nothing globally; instead run `git difftool -y --extcmd='<editor-diff-cmd>' base...head` in the worktree (`zed --diff` handles multiple files in one call; `code --diff` is per-pair). Cap it: no comment capture from ggh's side except in VS Code. Honest, cheap, and better than GitHub web for deep review because the IDE's semantic navigation wins.

### 2. `ggh review 42 --tui` — the flagship; only if it's first-class
Terminal review is worth it only with the modern stack, which conveniently is Bun-native: **OpenTUI + @pierre/diffs internals**, the exact combination proven by hunk, critique, and stage (all MIT — read their code). Ink is disqualified on perf evidence.

Architecture: `@opentui/core` renderer; file tree sidebar; diff stream with split/unified auto-switching on terminal width; Shiki tokens (JS-regex engine, lazy per-language) mapped to OpenTUI cells; row-viewport virtualization (mandatory for 5k+ lines); `n`/`N` hunk nav; `v` mark viewed (persist via ggh's existing local storage — a **local review ledger**); `c` comment on line/range (draft persisted, resumable like tuicr); `S` submit → existing `submitPullRequestReview`. Diff source: `getPullRequestDiff`, plus **"changes since your last review"** computed locally from the user's last review via the API — GitHub web's killer tracking feature, in the terminal. Fallback ladder when user hasn't opted in: shell to `tuicr pr 42` if installed (full loop already), else `delta`, else current `renderDiff`. Bundle: OpenTUI ships prebuilt platform binaries — **verify FFI embedding under `bun build --compile` first** (Bun supports embedded node addons; confirm before committing) and note ggh's npm distribution makes this a compile-target concern, not a blocker. OSC 1717 (delta emits, difftastic pending) is a watch-item for a hybrid "delta renders, ggh navigates" mode, not a foundation — it's a draft spec.

### 3. `ggh review 42 --web` — the T3-parity surface
When the terminal is too narrow for split view or the diff is huge, open a local page instead of a tab on github.com.

Architecture: `Bun.serve` bound to `127.0.0.1`, random port, 32-byte random token in the URL path, single-use server lifespan (SIGINT/exit kills it); embedded prebuilt assets (`bun build --compile` embeds files); vanilla-JS `@pierre/diffs` `FileDiff` with its annotation framework rendering comment widgets on line selection; comments POST back to ggh's GraphQL and appear as real PR review comments. This is **the same rendering stack T3 Code uses** — parity with the best agent host is the point — while beating GitHub web on: instant local load, no upload of private code to a browser tab, offline reading, and ggh-context integration (AI findings can be pinned as annotations next to the lines they concern). Feasibility from a Bun binary: proven pattern; critique already does TUI+web from one Bun codebase (though its `--web` uploads to a hosted URL — do the local-server variant instead for privacy).

## What NOT to build

- **A custom diff engine or custom ANSI renderer.** Structural diffing means maintaining 30+ tree-sitter grammars (difftastic's full-time job); pretty diffs mean years of delta polish. Compose, don't compete.
- **An Ink-based TUI.** Perf ceiling documented above.
- **diff2html or Monaco in the web viewer.** diff2html chokes on large diffs; Monaco is 5MB+ for what @pierre/diffs does better.
- **Kitty/sixel graphics-protocol rendering.** Nothing in the surveyed mainstream emits images in diffs; OpenTUI can show images if it ever matters. Niche rabbit hole.
- **A new pager to replace users' `core.pager`.** Interop beats replacement; ggh should *consume* delta/difft configs, not fight them.

## Bold option — `ggh review 42 --structural`: AI-free semantic review ledger

Ship a review mode that pipes the PR through **difftastic** (materialize base/head refs locally, run `difft` per file-pair or configure `git -c diff.external=difft diff --ext-diff`) **plus** ggh's local review ledger: hunk-granularity "viewed" state, changes-since-your-last-review computed locally, and comment capture on the *structural* hunks mapped back to GitHub line anchors. Nobody has this: GitHub web gives you the tracking but not structural rendering; difftastic gives rendering but no review state; tuicr gives review state but line-based diffs. ggh already owns the GitHub plumbing (anchored comments, review submission) that makes the mapping from AST-level hunks to `file:line` review comments tractable — the same anchoring logic `pr-review.ts` uses for AI findings. Caveats to state openly: difftastic's performance on very-high-churn files (cap: fall back to line diff per file above N changed lines, or honor its own fallback), and difftastic output is display-only — comments must anchor to real diff lines, so keep the unified diff alongside the structural view as the anchor source of truth.

## Bottom line

Build `--editor` immediately (trivial, genuinely superior for deep review). Build `--tui` on OpenTUI + @pierre/diffs with comment posting and the local ledger — the terminal review gap is real and the TS-native stack is finally good enough that "first-class" is achievable, not aspirational; if that investment isn't warranted, shell out to tuicr/delta instead of shipping something mediocre. Add `--web` with @pierre/diffs (T3-parity, local, comment-posting) for huge or split-view-hungry diffs. Skip everything in the NOT-build list.
